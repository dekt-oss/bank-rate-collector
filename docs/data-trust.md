# 이 데이터를 얼마나 믿을 수 있나

업무 근거로 쓰기 전에 읽는 문서다. 코드를 안 봐도 읽히게 썼다.

숫자는 전부 **2026-08-07 발행본에서 직접 잰 값**이다. 다시 재는 방법은 §5에 있다.

---

## 한 줄로

이 데이터가 보장하는 것은 **「원천이 그렇게 공시했다」까지**다.
**「그 금리가 실제로 적용된다」는 보장하지 않는다.**

둘의 차이가 이 문서 전부다. 앞쪽은 기계가 검사하고 증거를 남긴다. 뒤쪽은
지점에 전화해서 확인할 일이다.

---

## 1. 보장되는 것 — 기계가 매번 검사한다

### 1.1 모든 숫자는 원문의 특정 위치에서 왔다

관측 **287,682건 전부**가 세 가지를 갖고 있다. 하나라도 빈 행이 있으면 발행이
멈춘다.

| 칸 | 무엇 | 빈 행 |
|---|---|---:|
| `raw_artifact_id` | 어느 원본 파일에서 왔나 | 0건 |
| `base_source_locator` | 그 파일의 어느 자리인가 (예: `$[17].baseRate`) | 0건 |
| `source_record_hash` | 그때 그 행이 정확히 무엇이었나 | 0건 |

원본 파일 **10,559개**를 그대로 보관한다. 그래서 「이 3.40%는 어디서 나왔나」를
파일 이름과 그 안의 위치로 답할 수 있다. 이것이 이 데이터의 가장 강한 근거이고,
사실상 유일하게 강한 근거다.

### 1.2 못 읽은 값은 지어내지 않는다

읽지 못하면 **비우고 사유를 남긴다.** 그럴듯한 값을 채우지 않는다.

가장 큰 사례는 우대금리다. 새마을금고와 지역농축협은 **원천 화면에 우대금리 열
자체가 없다.** 그래서 해당 98,736행의 최고금리가 전부 비어 있다. 기본금리를
복사해 채우면 화면은 보기 좋아지지만 없는 사실을 만드는 것이다. 발행 게이트가
「채워진 값 0건」을 매번 확인한다.

### 1.3 발행 전에 38가지를 검사하고, 하나라도 실패하면 발행이 멈춘다

- **저장 검사 12가지** — 관측 존재, 원본 추적 누락, 금리 저장 형식, 업권별
  우대금리 규칙, 실행 내 중복, DB 무결성·외래키 등
- **완료 게이트 26가지** — 위에 더해 원본 보존, 업권 혼합 0, 금리 적용범위,
  manifest 해시 일치, API 키 노출 0 등

말뿐인 장치가 아니다. **2026-08-07에 실제로 두 번 멈췄다.** run 25·26이
게이트에서 실패해 발행 단계가 통째로 건너뛰어졌고, 그동안 화면은 옛 데이터를
계속 보여줬다(고쳐서 지금은 통과한다). 게이트가 통과를 안 시켜 주는 쪽으로
동작한 실증이다.

### 1.4 발행본은 해시로 봉인된다

발행되는 DB의 SHA256이 manifest에 적힌 값과 같은지, 표마다의 행 수가 실제
`COUNT(*)`와 같은지 매번 대조한다. 화면에 표시된 숫자가 `summary.json`과
같은지도 대조한다. 중간에 바뀌면 발행이 멈춘다.

### 1.5 언제 무엇을 받았는지가 다 남는다

수집 실행 **37건**의 이력이 있고, 실행마다 원천·시작·종료·건수·오류 수가 있다.
가장 최근 한 바퀴는 이렇다.

```
finlife_savings_bank  success   4,006건   오류 0
finlife_bank          success     333건   오류 0
fsb                   success   3,767건   오류 0
cu                    success  30,994건   오류 0
kfcc                  success  93,816건   오류 0
nh_local              success   4,920건   오류 0
```

## 2. 보장되지 않는 것 — 반드시 같이 알아야 한다

### 2.1 원천이 틀리면 우리도 틀리다

우리는 공시 화면의 사본을 만든다. 원천이 잘못 올렸으면 그 잘못이 그대로 온다.
우리가 잡을 수 있는 것은 「형식이 깨진 것」이지 「내용이 틀린 것」이 아니다.

### 2.2 수집 범위가 업권마다 달랐다 — 이게 가장 오해를 부른다

화면의 건수는 **업권의 크기가 아니라 우리가 받아 온 양**이다. 실제로 오해가
있었다.

| 업권 | 화면 행 | 실제 규모 (원천 실측) |
|---|---:|---|
| 새마을금고 | 93,816 | 1,260개 금고 / 3,135개 점포 |
| 지역농축협 | 4,920 | **4,871개 점포** |

점포는 농축협이 더 많은데 화면에서는 1/19로 보였다. **부산 120곳만 받았기
때문이다.** 2026-08-07에 전국으로 넓혔다.

새마을금고도 **1,156곳**만 들어와 있다. 명부 실측 1,260곳과 104곳 차이가 나고,
원인은 아직 확인되지 않았다.

> 건수를 시장 점유율이나 상품 수 비교에 쓰지 말 것. 그 용도로 만들어지지 않았다.

### 2.3 오래된 공시일이 섞여 있다

공시일이 2026년이 아닌 행이 **698건** 있다. 가장 오래된 것은 2015년이다.
상품이 없어진 것인지 금리가 오래 안 바뀐 것인지는 **이 자료로 구분할 수 없다.**
화면은 1년 넘은 행에 「오래됨」 표식을 붙인다.

```
2026년  133,151     2024년  197     2021년   36
2025년      334     2023년   62     2020년   11
                    2022년   52     2016년 이전  6
```

### 2.4 「지역」의 뜻이 원천마다 다르다

같은 「부산」이라도 근거가 다르다. 화면은 행마다 배지로 이 차이를 밝힌다.

| 업권 | 지역의 뜻 | 구·군까지 |
|---|---|---|
| 새마을금고 | 점포 주소 | 가능 |
| 지역농축협 | 점포 주소 | 가능 |
| 저축은행 | **본점 소재지** — 그 지점 금리가 아니다 | 불가 |
| 신협 | **조회 조건** — 그 지역에서 영업한다는 뜻 | 불가 |
| 시중은행 | 전국 공시 | 불가 |

저축은행에서 「부산 동구」는 **본점이 동구에 있다**는 뜻이지 동구 지점 금리가
아니다. 이걸 지점 금리로 읽으면 틀린다.

### 2.5 우대금리는 3분의 2가 「원천 미제공」이다

| 판정 | 행 | 뜻 |
|---|---:|---|
| 원천 미제공 | 93,895 | 원문에 우대조건 항목 자체가 없다 |
| 명시적 없음 | 31,986 | 원문이 「해당사항없음」이라 적었다 |
| 있음 | 7,968 | 우대조건이 적혀 있다 |

「원천 미제공」과 「우대조건 없음」은 **다르다.** 앞은 모르는 것이고 뒤는 아는
것이다. 이 둘을 합쳐 「우대 없음」으로 세면 안 된다.

### 2.6 이용약관을 확인하지 못한 원천이 있다

저축은행중앙회와 신협은 수집 허용 범위를 확인하지 못했다. 차단 신호가 오면
우회하지 않고 그 자리에서 멈추도록 해 뒀지만, **정책상 허용된다는 확인은 아직
없다.** 대외로 재배포하기 전에는 이 점을 따로 확인해야 한다.

## 3. 업무에 쓸 때 — 말해도 되는 것과 안 되는 것

| 이렇게는 말해도 된다 | 이렇게 말하면 안 된다 |
|---|---|
| 「2026-08-07 기준 A금고가 공시한 12개월 정기예탁금 기본금리는 3.40%다」 | 「A금고에 가면 3.40%를 받는다」 |
| 「B저축은행의 **본점 소재지**는 부산 동구다」 | 「부산 동구 B저축은행 지점 금리는 …」 |
| 「이 화면에 들어온 새마을금고는 1,156곳이다」 | 「전국 새마을금고는 1,156곳이다」 |
| 「새마을금고는 원천이 우대금리를 공시하지 않는다」 | 「새마을금고는 우대금리가 없다」 |
| 「수집된 범위 안에서 최고금리 상단은 5.00%다」 | 「전국 최고금리는 5.00%다」 |

**실제 거래 조건은 반드시 해당 기관에 확인한다.** 이 데이터는 어디에 전화할지
좁히는 데 쓰는 것이지, 전화를 대신하는 것이 아니다.

## 4. 남이 검증할 수 있게 만든 장치

「믿어 달라」가 아니라 「확인해 보라」로 답할 수 있어야 한다.

1. **원자료를 통째로 내려받을 수 있다.** 화면 하단에서 CSV와 JSON 전체를 받는다.
   화면에 보이는 100행이 아니라 전량이다.
2. **수집원마다 무엇을 어떻게 받았는지 적어 뒀다.** 화면 하단 주석에 원천 이름,
   수집 방식, 그 원천의 지역이 무엇을 뜻하는지가 있다.
3. **모든 실행 로그가 공개돼 있다.** 저장소의 Actions에서 언제 무엇을 몇 건
   받았는지, 게이트 38항목이 각각 통과했는지 줄 단위로 볼 수 있다.
4. **정찰 기록이 저장소에 있다.** `docs/source-recon/`에 원천별로 어떤 요청을
   보내면 무엇이 오는지, 어디서 틀렸다가 고쳤는지가 남아 있다.
5. **틀렸던 판정을 지우지 않는다.** 명세서에 정정 절을 앞에 붙이고 원문은 남긴다.
   무엇을 잘못 알았다가 언제 고쳤는지가 이력으로 보인다.

## 5. 이 문서의 숫자를 다시 재는 법

전부 2026-08-07 발행본 기준이다. 데이터가 바뀌면 이 문서도 같이 고친다.

```bash
# 화면이 실제로 읽는 파일을 받아서 직접 센다
curl -sO https://bank-rate-collector-dekt-oss-projects.vercel.app/data/table.json

# 발행 시각과 행 수
curl -s https://bank-rate-collector-dekt-oss-projects.vercel.app/site-manifest.json
```

관측·기관 수와 실행 이력은 화면 상단과 하단에 그대로 나온다. 게이트 38항목의
통과 여부는 Actions의 `Verify P1-A gate`와 `Validate stored data` 단계에 있다.
