# 고려저축은행 수신금리 예측 보정용 내부데이터 요청서 v1

```yaml
document_type: internal_data_request
status: ready_to_send
date: 2026-08-18
purpose: Deposit Pricing Engine calibration
repository: dekt-oss/bank-rate-collector
contains_customer_pii: false
preferred_history: 36_months
minimum_history: 24_months
preferred_granularity: daily
```

---

# 0. 요청 목적

금리수집기의 수신 시뮬레이터를 실제 고려저축은행 수신실적으로 보정하기 위한 자료 요청이다.

최종적으로 알고 싶은 것은 다음이다.

> **당사 예금금리를 변경했을 때 신규수신·재예치·이탈·순수신이 실제로 얼마나 변하는가?**

그리고 최종적으로:

> **목표 순수신을 달성하기 위한 최소 금리를 얼마로 설정해야 하는가?**

를 계산하는 것이 목적이다.

개인 고객명, 계좌번호, 주민번호 등 개인정보는 필요하지 않다.

가능하면 **상품 × 기간 × 채널 × 일자 단위 집계 데이터**로 제공한다.

---

# 1. 요청 기간 / 데이터 단위

## 기간

권장:

```text
최근 36개월
```

최소:

```text
최근 24개월
```

12개월 이하만 있으면 계절성·금리국면 변화와 실제 금리효과를 분리하기 어렵다.

---

## 시간 단위

우선순위:

1. 일별
2. 주별
3. 월별

월별만 가능해도 초기 탐색은 가능하지만 금리변경 직후 반응과 특판 효과 분리가 어려워진다.

---

# 2. P0 — 반드시 필요한 핵심 데이터

아래 항목은 실제 금리-수신 민감도 calibration을 위한 최소 요구사항이다.

---

## Dataset A. 상품별 신규수신/잔액/금리

권장 파일명:

```text
A_product_daily_deposit_performance.csv
```

필수 열:

| 필드 | 설명 | 예시 |
|---|---|---|
| `date` | 기준일 | 2026-07-01 |
| `product_id` | 내부 상품 식별자 | TD001 |
| `product_name` | 상품명 | 정기예금 |
| `product_type` | 예금/적금 등 | term_deposit |
| `term_months` | 가입기간 | 12 |
| `channel` | 영업점/인터넷/모바일 등 | mobile |
| `base_rate` | 해당일 기본금리 | 3.30 |
| `max_rate` | 해당일 공시 최고금리 | 3.50 |
| `actual_applied_rate` | 실제 신규취급액 가중평균 적용금리 | 3.44 |
| `new_amount` | 신규취급액 | 12500000000 |
| `new_accounts` | 신규계좌 수 | 421 |
| `ending_balance` | 해당 상품 일말 잔액 | 85000000000 |

### `actual_applied_rate`가 중요한 이유

공시 최고금리와 고객이 실제 받은 평균금리는 다를 수 있다.

모델은 실제 고객 반응을 보정해야 하므로 가능하면:

```text
신규취급액 가중평균 실제 적용금리
```

을 요청한다.

불가능하면 `base_rate`, `max_rate`만 먼저 제공하고 실제 적용금리는 후속으로 보완한다.

# 3. P0 — 금리변경/특판 이벤트 데이터

금리가 올랐을 때 수신이 늘었다고 해서 항상 금리 때문인 것은 아니다.

특판, 앱푸시, 광고, 판매한도 등이 동시에 바뀌었을 수 있다.

따라서 아래 이벤트 이력이 필요하다.

권장 파일명:

```text
D_product_campaign_events.csv
```

필드:

| 필드 | 설명 |
|---|---|
| `event_id` | 이벤트 식별자 |
| `product_id` | 대상 상품 |
| `start_date` | 시작일 |
| `end_date` | 종료일 |
| `event_type` | 특판/금리변경/캠페인/채널프로모션 등 |
| `rate_before` | 변경 전 금리 |
| `rate_after` | 변경 후 금리 |
| `sales_cap_amount` | 판매한도, 있으면 |
| `channel` | 대상 채널 |
| `push_or_ad` | 앱푸시/광고 여부 |
| `note` | 기타 설명 |

최소한 `금리변경일`, `특판기간`, `판매한도`는 확보하는 것이 좋다.

# 4. P0 — FTP / 내부 조달원가

최종 목표가 단순 수신액 최대화가 아니라 **최소비용으로 필요한 수신 확보**이므로 FTP가 필요하다.

권장 파일명:

```text
E_ftp_curve.csv
```

필수 열:

| 필드 | 설명 |
|---|---|
| `date` 또는 `month` | 적용시점 |
| `term_months` | 기간 |
| `ftp_rate` | 내부 FTP |

가능하면 추가:

| 필드 | 설명 |
|---|---|
| `target_margin` | 목표 스프레드/마진 |
| `liquidity_premium` | 내부적으로 별도 관리 시 |
| `funding_cost_basis` | FTP 산출 기준 설명 |

FTP가 없으면 E1 수신액 예측은 가능하지만,
E2 `목표 순수신을 만족하는 최소 조달비용 금리` 최적화는 완성되지 않는다.

# 5. P1 — 모델 정확도를 크게 높이는 선택 데이터

아래는 필수는 아니지만 확보 가능하면 모델 품질이 크게 좋아진다.

---

## 고객군 — 익명 집계만

개인 식별자는 필요 없다.

추천 차원:

```text
개인 / 법인
신규고객 / 기존고객
금액구간
연령구간(필요 시, 익명 집계)
지역
```

예:

```text
2026-07-01
12M 정기예금
모바일
기존고객
개인
1천만~5천만원
신규수신 18억원
```

금리 민감도가 고객군별로 다를 수 있기 때문에 유용하다.

---

## 채널 세분화

가능하면:

- 영업점
- 인터넷
- 모바일
- 제휴
- 특판전용

을 유지한다.

채널을 모두 합산하면 금리효과와 채널효과가 섞일 수 있다.

---

## 우대조건 실제 달성 정보

가능한 경우:

| 필드 | 설명 |
|---|---|
| `product_id` | 상품 |
| `date/month` | 시점 |
| `eligible_accounts` | 우대 대상 |
| `achieved_accounts` | 실제 달성 |
| `avg_bonus_rate` | 실제 평균 우대금리 |

이 데이터가 있으면 Stage D의 `우대조건 난이도/실질 적용률`을 추정할 수 있다.

현재는 없어도 된다.

# 6. 데이터 정의 확인이 필요한 항목

자료를 받을 때 아래 정의를 같이 확인해야 한다.

## 신규수신

`new_amount`가 정확히 무엇인지:

- 신규 계좌 개설금액만인지
- 기존 고객 추가납입 포함인지
- 재예치가 포함되는지

재예치와 신규수신은 모델에서 분리할 예정이므로 중복 여부가 중요하다.

---

## 재예치

재예치의 업무 정의를 확인한다.

예:

- 동일 상품 재가입만 재예치인지
- 다른 당사 정기예금으로 이동해도 재예치인지
- 며칠 이내 재가입을 재예치로 보는지

---

## 순수신

은행 내부에서 사용하는 공식 순수신 정의가 있으면 그 정의를 우선한다.

없으면 모델 초안은 다음 구조를 검토한다.

```text
순수신
= 신규유입
+ 재예치
- 만기이탈
- 중도해지 등 기타유출
```

단 신규수신/재예치 집계 정의에 따라 중복 제거가 필요하다.

---

# 7. 단위 규칙

가능하면 원자료는 금액을 원 단위 정수로 제공한다.

```text
12500000000
```

화면/모델 출력 단계에서 억원 단위로 변환한다.

금리는 `%` 단위 권장:

```text
3.50 = 연 3.50%
0.10%p = 10bp
```

모든 파일에서 단위를 통일한다.

---

# 8. 개인정보 / 보안

필요하지 않은 항목:

- 고객명
- 주민등록번호
- 전화번호
- 주소 상세
- 계좌번호
- CIF 등 개인식별 가능 ID

원칙적으로 익명 집계 데이터만 사용한다.

내부 원자료를 GitHub repository에 직접 커밋하지 않는다.

분석용 데이터 저장위치와 접근권한은 실제 자료 제공 전에 별도 결정한다.

# 9. 실제 요청용 요약문

아래 문구를 내부 데이터 담당자에게 그대로 전달할 수 있다.

---

## 수신상품 금리효과 분석용 데이터 요청

수신상품 금리 변경이 신규수신·재예치·순수신에 미치는 영향을 분석하기 위해 아래 자료를 요청드립니다.

**기간:** 최근 36개월 권장, 최소 24개월  
**단위:** 일별 권장, 불가 시 주별  
**개인정보:** 불필요, 상품/기간/채널별 집계 데이터만 요청

### 필수

1. 상품별 일자별 적용금리
   - 상품코드/상품명
   - 가입기간
   - 채널
   - 기본금리
   - 최고금리
   - 가능 시 실제 신규취급액 가중평균 적용금리

2. 상품별 일자별 신규수신
   - 신규취급액
   - 신규계좌 수
   - 일말잔액

3. 만기 및 재예치
   - 만기도래액/계좌수
   - 재예치액/계좌수
   - 가능 시 재예치 상품/기간/적용금리

4. 중도해지
   - 중도해지 금액/계좌수

5. 금리변경·특판·캠페인 이력
   - 적용기간
   - 변경 전/후 금리
   - 판매한도
   - 채널
   - 광고/앱푸시 여부

6. 기간별 FTP
   - 시점
   - 기간
   - FTP 금리

### 있으면 추가

- 개인/법인
- 신규/기존 고객
- 금액구간
- 지역
- 우대조건 실제 달성률

고객명·계좌번호·주민번호 등 개인식별정보는 필요하지 않습니다.

---

# 10. 수령 후 첫 검증

자료 수령 즉시 모델을 학습하지 않는다.

먼저 다음을 확인한다.

1. 기간 연속성
2. 금리변경일과 실제 적용금리 일치
3. 신규수신과 재예치 중복 여부
4. 만기도래액과 재예치액 정의
5. 잔액 증감과 flow 항목 tie-out
6. 특판/캠페인 누락 여부
7. FTP 기간매칭
8. 상품코드 변경/통합 이력
9. 결측·0의 의미
10. 일/주/월 집계시점 기준

위 data quality gate를 통과한 뒤 E1 calibration을 시작한다.
