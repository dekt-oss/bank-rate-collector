# 원천 정찰: 저축은행중앙회(FSB) 소비자포털

정찰 실행: 2026-08-05, `scripts/p1b_fsb_recon.py`
기계 판독 보고서: `docs/source-recon/fsb-recon.json`
표본: `tests/fixtures/fsb/`

이 문서는 **정찰 기록**이다. 파서 설계가 아니다. 확인한 사실과 확인하지
못한 것을 구분해 적는다. 명세서 v3 §22("실물 표본 없이 파서를 추정 구현하지
않는다")를 지키기 위한 선행 단계다.

---

## 1. 가장 중요한 결론부터

**FSB도 본점 기준 공시다. 부산 구·군 단위 지점 금리는 여기서도 나오지 않는다.**

화면이 스스로 그렇게 밝힌다. 원문 그대로:

> 본 화면에 고시된 금리는 저축은행의 **본점 기준**이며, 좀 더 자세한
> **지점별 금리는 해당 저축은행으로 연락**하시기 바랍니다.

명세서 v3의 계획은 FSB를 저축은행 1차 원천으로 두고 finlife를 교차검증으로
쓰는 것이었다. 그 배치는 유효하다 — FSB 쪽 데이터가 훨씬 풍부하다. 다만
**"FSB를 붙이면 부산 지점 금리가 나온다"는 기대는 성립하지 않는다.**
저축은행 부문은 원천적으로 구·군 단위를 제공하지 않는다.

부산 구·군 단위는 여전히 새마을금고(세로 절단 2)에서만 나온다.

## 2. finlife 대비 실제로 나아지는 점

| 항목 | finlife | FSB |
|---|---|---|
| 지역 차원 | **없음** | 시도 단위 `AREA` 필터 있음 (`YN_Busan` 등 17개) |
| 우대조건 | `spcl_cnd` 텍스트 | `SWEETENER` + `ETC_NOTE_MATTER` + `JOIN_TARGET` |
| 가입방법 | 없음 | `JOIN_LOCATION` — 영업점/인터넷/스마트폰/모집인/전화/기타 |
| 만기후이율 | 없음 | `EXPIRE_INTRST_RATE` |
| 상품 링크 | 없음 | `PRODUCT_URL`, `URL` |
| 공시일 | `dcls_strt_day` | `START_DATE`, `SUBMIT_MONTH`, `FINAN_COMP_SUBMIT_DATE`, `CHG_DATE` |

`JOIN_LOCATION`은 우리 `join_channel` 열거형과 그대로 대응한다. finlife에는
이 차원이 없어 지금은 전부 `any`로 저장하고 있다.

### `AREA` 필터의 정확한 의미 — 주의

지역별 건수는 실제로 달라진다 (12개월 정기예금, 2026-08-05 기준):

| AREA | 건수 |
|---|---|
| 지역전체 | 397 |
| `YN_Seoul` | 163 |
| `YN_Busan` | 67 |

다만 **평균금리(`DAN12`)는 세 경우 모두 3.8로 동일하다.** 즉 화면 상단의
평균금리는 지역 필터를 반영하지 않는 전국 평균이다. 이 값을 "부산 평균"으로
표시하면 안 된다.

`YN_` 접두사와 위 유의사항을 함께 보면 `AREA`는 **해당 지역에서 가입 가능한
저축은행을 고르는 필터**이지 지점별 금리를 주는 차원이 아니다. 따라서 FSB를
붙였을 때 얻는 것은 이렇게 적어야 한다.

```
부산에서 가입 가능한 저축은행의 본점 기준 공시금리
```

`부산 저축은행 지점 금리`가 아니다.

## 3. 접근 경로 — 실측

### 3.1 화면

사이트 내비게이션에서 추출했다. 명세서 v3 §7.2가 지정한 세 화면이 모두 있다.

| 경로 | 화면 | 정찰 결과 |
|---|---|---|
| `ratedepo_0100.act` | 정기예금 | 확인 |
| `rateinst_0100.act` | 정기적금 | 확인 |
| `ratanym_0100.act` | 입출금자유예금 | **미해소** (§5) |

명세서 v3 §7.2가 적어둔 `rateinfo_0100.act`는 **존재하지 않는다.** 200을
돌려주지만 내용은 "요청하신 페이지를 찾을 수 없습니다"인 소프트 404다.
상태 코드만 보고 성공으로 판정하면 안 되는 사례다.

### 3.2 데이터는 HTML에 없다

화면 HTML에는 금리 행이 하나도 없다. 표는 헤더만 있고 본문은 비어 있으며,
평균금리 자리도 `0.00%`다. 전부 AJAX로 실린다. 화면 HTML을 파싱하는 접근은
성립하지 않는다.

### 3.3 실제 엔드포인트 — 확장자가 `.act`가 아니다

`jexjs.createAjaxUtil(...)`이 URL을 조립하는데, 접미사가 `FSBcomm.js`에
있다.

```js
var ajaxSetup = { contextPath: "", prefix: "", suffix: ".jct", ... };
```

그래서 실제 데이터 엔드포인트는 **`.jct`**다. 화면마다 규칙이 다르다.

| 화면 | 엔드포인트 | 응답 키 |
|---|---|---|
| 정기예금 | `POST /ratedepo_0100_01.jct` | `REC`, 총건수는 행의 `CNT` |
| 정기적금 | `POST /rateinst_0100_01.jct` | `REC`, 총건수는 행의 `CNT` |
| 입출금자유예금 | `POST /ratanym_0100.jct` (`_01` 없음) | `ANYM_REC`, `TOTAL_CNT` |

`Content-Type: application/json`으로 POST한다. 화면을 먼저 GET해 세션 쿠키를
받아야 한다.

### 3.4 요청 본문

정기예금·정기적금 (`ratedepo_0100.js`의 `depo_search()`에서 읽음):

```json
{"REG_DATE":"2026-08-05","CHG_DATE":"2026-08-05","AREA":"YN_Busan",
 "SELECT_YEAR":"2026","SELECT_MONTH":"08","SELECT_DAY":"05",
 "TB_SEQ1":"","TB_SEQ2":"","TB_SEQ3":"","ORDERBY":"",
 "JOIN_LOCATION":"1|2|3|4|5|9","CHK_MONTH":"12",
 "END_NUM":"10","START_NUM":"1",
 "SEARCH_CODE":"","SEARCH_SELECT_IN":"","SEARCH_TEXT_IN":""}
```

`TB_SEQ1~3`, `SEARCH_CODE`의 의미는 **모른다.** 빈 값으로 두면 동작한다.
의미를 알아내기 전까지 채우지 않는다.

### 3.5 조회 차원

화면에서 읽은 값이다. 하드코딩이 아니라 정찰 스크립트가 라벨까지 추출한다.

- **가입기간** (`radio1`): 1 / 3 / 6 / 12 / 24 / 36 개월
- **가입방법** (`chkbox01` → `JOIN_LOCATION`): 1 영업점(창구방문), 2 인터넷,
  3 스마트폰, 4 모집인, 5 전화(텔레뱅킹), 9 기타
- **지역** (`areaSelect` → `AREA`): 지역전체 + 16개 시도. 부산은 `YN_Busan`
- **이자지급방식**: 단리·복리가 행 안에 별도 필드로 함께 온다 (§4)

### 3.6 조회 가능 기간

`fn_searchDepo()`에 이런 분기가 있다.

```js
if (REG_DATE < "2026-01-22") { ... location.href = "ratedepo_old_0100.act"; }
```

2026-01-22 이전 금리는 이 화면에서 나오지 않고 `ratedepo_old_0100.act`(16~25년),
`ratintedein_0100.act`(~15년)로 갈린다. 과거 이력이 필요하면 별도 정찰 대상이다.

### 3.7 엑셀 다운로드

화면에 `<form id="xlsdown" action="ratedepo_0100_02.act" method="post">`가 있다.
명세서 v3 §7.2가 1순위로 둔 "공식 엑셀 다운로드 요청 재현"이 가능해 보인다.
다만 이번 정찰에서 **실제로 호출해보지 않았다.** JSON 엔드포인트가 이미
필요한 필드를 전부 주므로 엑셀이 꼭 필요한지부터 판단해야 한다.

## 4. 응답 필드 — 실물

정기예금 29개 필드, 정기적금 31개 필드. 정기적금에만 `BANK_CODE`,
`TOP_CREDIT`이 더 있다.

명세서 v3 §7.2가 요구한 필수 필드와의 대응:

| 명세서 요구 | FSB 필드 | 확인 |
|---|---|---|
| 저축은행명 | `BANK_NAME` | 있음 (우측 공백 패딩 있음, 예: `'BNK                 '`) |
| 상품명 | `PRODUCT_NAME` | 있음 |
| 기본금리 | `JUNG_12M_DAN` / `JUNG_12M_BOK` | 있음 |
| 최고우대금리 | `TOP_12M_DAN` / `TOP_12M_BOK` | 있음 |
| 가입방법 | `JOIN_LOCATION` | 있음 |
| 상품 상세·우대조건 | `SWEETENER`, `ETC_NOTE_MATTER`, `JOIN_TARGET`, `PRODUCT_URL` | 있음 |
| 조회일·공시일 | `START_DATE`, `SUBMIT_MONTH`, `FINAN_COMP_SUBMIT_DATE`, `CHG_DATE`, `REG_DATE` | 있음 |

### 식별자

- `FINAN_COMP_CODE` (예: `0013002`) — 기관 코드
- `FINAN_PROD_CODE` (예: `BNK1003`, `BNK5003`) — 상품 코드
- `TB_SEQ` (예: `868751`) — 행 일련번호

기관·상품 코드가 모두 있으므로 `source_entity_links`에 붙일 안정 키가 확보된다.
**finlife의 `fin_co_no`와는 다른 체계로 보인다** — 대조는 아직 하지 않았다.

### 금리 필드 구조 — 파서 설계 시 주의

기간이 **행 필드가 아니라 요청 차원**이다. `CHK_MONTH=12`로 요청하면 행에는
`JUNG_12M_DAN` / `TOP_12M_DAN` / `JUNG_12M_BOK` / `TOP_12M_BOK`만 온다.
6·24·36개월을 얻으려면 요청을 나눠야 한다.

한 행에 단리·복리가 함께 오므로, 우리 스키마 기준으로는 **한 행이 최대 2개의
비교 단위(`product_variant`)로 펼쳐진다.** 명세서 v3 §7.2의 "동일 상품이
단리·복리로 중복 노출되는 경우 옵션으로 분리한다"가 바로 이 지점이다.

### 개인정보성 필드

`OWNER` 필드에 담당 부서명과 전화번호가 들어온다 (예: `경영기획부, 0517131215`).
업무 연락처이고 공개 공시 항목이지만, 수집 대상에 넣을 이유가 없다.
**파서에서 버린다.**

## 5. 미해소 항목

| 항목 | 상태 |
|---|---|
| 입출금자유예금 수집 | **미해소.** `ratanym_0100.jct`가 `{"COMMON_HEAD":{...}}`만 돌려주고 `ANYM_REC`가 없다. `ratanym_0100.js`의 `sendData` 초기값과 화면 기본 선택값을 그대로 보냈는데도 비어 있다. 추가로 필요한 값이 있거나 NetFunnel 대기열이 관여하는 것으로 보이나 확인하지 못했다 |
| `TB_SEQ1~3`, `SEARCH_CODE` 의미 | 미확인. 빈 값으로 동작하므로 지금은 비워 둔다 |
| 엑셀 다운로드 (`_02.act`) | 호출해보지 않음 |
| finlife 기관코드와의 대응 | 미확인. `cross_source_difference` 검수항목을 만들려면 먼저 이 매핑이 필요하다 |
| 과거 금리 화면 | 2026-01-22 이전은 별도 화면. 정찰하지 않음 |
| 호출 한도·차단 정책 | 미확인. robots.txt가 없다(요청 시 사이트 index를 돌려준다). 이번 정찰은 총 20회 미만, 1초 간격으로 보냈다 |
| 이용약관상 수집 허용 범위 | 미확인. `source.policy_status` 판정 전 확인 필요 |

## 6. P1-B 착수 판단

**착수 가능하다.** 정기예금·정기적금 두 화면은 실물 표본과 필드 구조가
확보됐고, 필수 필드가 전부 있으며, 안정 식별자도 있다. 이 두 화면만으로
명세서 v3 §7.2의 주요 요구를 충족한다.

다만 착수 전에 정해야 할 것이 있다.

1. **입출금자유예금을 P1-B 범위에 넣을지.** 지금 상태로는 수집할 수 없다.
   빼고 가거나, 먼저 §5의 미해소를 푼다.
2. **기간별 요청 분할 비용.** 6개 기간 × 2개 화면 = 12회 요청이 최소다.
   지역까지 나누면 곱해진다. 지역 전체를 한 번에 받고 우리 쪽에서 나누는
   편이 나을 수 있다 — 다만 `AREA`가 행 필드로 오지 않으므로, 지역별로
   나눠 받지 않으면 어느 은행이 부산에서 가입 가능한지 알 수 없다.
   **이 선택은 P1-B 설계에서 명시적으로 결정해야 한다.**
3. **표기 규율.** §1 결론에 따라 P1-B 산출물에도 "본점 기준" 표기가 그대로
   유지된다. 지역 필터가 생겼다고 해서 `부산 저축은행 금리`로 바꿔 쓰지 않는다.
