## 1. 도달성 판정 — 실행 위치가 결정적이다

`scripts/p0_kfcc_probe.py` 실행 결과, **같은 요청이 실행 위치에 따라 다른 결과**를 낸다.

| 실행 위치 | `robots.txt` | `map/main.do` | `map/list.do?r1=부산&r2=중구` | 판정 |
|---|---|---|---|---|
| 개발 컨테이너 (Claude Code 세션) | `400 Request Blocked` | `400 Request Blocked` | 미시도 (차단 즉시 중단) | **차단** |
| GitHub Actions 러너 (ubuntu-latest) | `200 OK` | `200 OK` | `200 OK` | **정상** |

프록시 상태(`__agentproxy/status`)는 `recentRelayFailures: []`로 정상이었고 GitHub·raw.githubusercontent 요청은
같은 경로로 성공했다. 따라서 차단 주체는 프록시가 아니라 새마을금고 측 접근제어로 판단된다.

### 결론

- `kfcc_official` 수집기는 **GitHub Actions 러너에서 실행**해야 한다.
- 개발 컨테이너에서는 공식 사이트 파싱을 실물로 검증할 수 없다.
  따라서 파서 개발은 **Actions에서 내려받은 원본 HTML fixture를 아티팩트로 가져와** 진행한다.
  (명세서 v3 §22 "실물 표본 없이 HTML 파서를 추정 구현하지 않는다" 준수)
- 차단 우회는 시도하지 않는다 (명세서 v3 §0.2, §16.1).

### 1.1 정정 — 개발 컨테이너에서도 열린다 (2026-08-05 재측정)

위 차단 판정은 **더 이상 유효하지 않다.** 같은 요청을 다시 보내니 개발
컨테이너에서도 정상 응답한다.

| 요청 | 최초 측정 | 재측정 |
|---|---|---|
| `map/main.do` | `400 Request Blocked` | `200` (12,831 bytes) |
| `map/list.do?r1=부산&r2=중구` | 미시도 | `200` (28,855 bytes) |

목록 페이지 크기가 최초 Actions 실측 fixture와 같은 28,855 bytes다.

우회 시도는 하지 않았다. 요청 방식은 그대로이고 상대 쪽 접근제어가 달라진
것으로 보인다. 따라서 **파서 개발과 검증을 개발 컨테이너에서 직접 할 수 있다.**
다만 이 상태가 유지된다는 보장이 없으므로 수집 워크플로우는 계속 Actions에서
돌리고, 차단이 다시 나타나면 `SourceBlockedError`로 처리한다.

`robots.txt`는 `200`을 주지만 내용이 HTML 문서다. 즉 robots.txt가 없고 소프트
404를 돌려주는 것이다. 크롤링 지침으로 삼을 수 없다.

### 2.2 금리 페이지 — 실물 확인 완료 (2026-08-05 2차 정찰)

> **이 절의 앞선 판정은 틀렸다.** 「금리」 버튼이 `view.do`를 부르는 것까지는
> 맞지만, 거기서 끝난다고 보고 "`goods_19.do`는 존재하지 않는다"고 적었다.
> `view.do`는 **iframe 껍데기**이고 그 안에서 `goods_19.do`를 부른다.
> 명세서 v3 §7.3.3의 `OPEN_TRMID`·`gubuncode` 가정은 **맞았다.**

「금리」 버튼의 1차 호출은 이렇다.

```javascript
function view_rate(elm) { _view(elm, "sub_tab_rate"); }
function _view(elm, tabId) {
  var param = M4Dom.loadSpanSection(trElm);   // 행의 숨김 span 전부
  param.tab = tabId;
  M4Ajax.actionForm("view.do", param, { method: "get" });
}
```

그런데 `view.do?tab=sub_tab_rate` 응답은 8,387 bytes짜리 껍데기이고 금고
정보표(금고명·구분·주소·전화·팩스)만 들어 있다. **금리 표가 없다.**
금리는 iframe에 form submit으로 실린다.

```javascript
mapform.action = "/map/goods_19.do?OPEN_TRMID=1203";
mapform.target = "rateFrame2";
mapform.submit();
```

#### 실제 수집 경로

```yaml

  path: /map/goods_19.do
  method: GET                    # form은 POST지만 GET으로도 같은 응답이 온다
  params:

    gubuncode: 12 | 13 | 14      # 상품군
```

| `goods_12/13/14/17/18/20.do` | **404** |

| `gubuncode` | h3 제목 | 표 헤더 |

| 13 | 거치식예탁금 기본이율 | `상품명 / 계약기간 / 월지급식 기본이율 / 만기지급식 기본이율` |
| 14 | 적립식예탁금 기본이율 | `상품명 / 계약기간 / 기본이율` |

```

```
→ `join_channel = branch`. 인터넷·모바일 금리가 아니다.

#### 구조 선택자 — 명세서 §7.3.5의 `#divTmp1` 가정은 **맞다**

> 한때 이 문서는 "`divTmp1/2/4`는 JS의 `getElementsByName` 대상일 뿐 실제
> DOM 컨테이너가 아니다"라고 적었다. **틀렸다.** 그 판정은
> `gubuncode`를 빼고 요청한 응답(=요구불, 12번)만 보고 내린 것이었다.
> 요구불 화면에만 `divTmp`가 없다.

`gubuncode=13`·`14`에서 `divTmp`는 실제 `<div>` 컨테이너이고 상품군별로
역할이 나뉜다. 개수가 고유 상품 수와 정확히 일치한다.

| 컨테이너 | 담는 표 | 13번 | 14번 |
|---|---|---|---|
| `divTmp1` | **기본이율 (수집 대상)** | 4개 | 9개 |
| `divTmp2` | 중도해지이율 | 4개 | 8개 |
| `divTmp4` | 만기후이율 | 4개 | 8개 |

각 컨테이너 안의 구조:

```html
<div id="divTmp1" name="divTmp1" style="display: block">
  <div class="tbl-tit">정기예탁금</div>
  <table class="rowTbl2" summary="...">
    <thead><tr><th>상품명</th><th>계약기간</th>
               <th>월지급식 기본이율</th><th>만기지급식 기본이율</th></tr></thead>
    <tbody>
      <tr><td rowspan="8" scope="row">정기예탁금</td>
          <td>1개월 이상</td><td>연0.0%</td><td>연0.0%</td></tr>
      <tr><td>3개월 이상</td><td>연1.8%</td><td>연1.8%</td></tr>
```

**파서는 `divTmp1`만 믿지 않는다.** 요구불에는 없고, 컨테이너 이름은 화면
구현 세부사항이라 언제든 바뀔 수 있다. `divTmp1`으로 후보를 좁히되
헤더 문자열(`상품명` + `…기본이율`)로 한 번 더 확인한다. 둘 중 하나만으로도
동작하도록 만들어 한쪽이 사라져도 조용히 틀리지 않게 한다.

#### `rowspan` — 열 정렬이 행마다 다르다

상품명 셀에 `rowspan`이 걸려 **첫 행만 상품명 칸을 갖고 나머지 행은 없다.**
위 예에서 첫 행은 `td` 4개, 둘째 행부터는 3개다. 열 인덱스를 고정하면
둘째 행부터 계약기간을 상품명으로 읽는다. 표본에서 `rowspan` 값은
13번에 8회(3~12), 14번에 17회(1~7) 나온다.

#### 한 상품에 표가 셋이다 — 파서가 반드시 걸러야 한다

`.tbl-tit`은 상품 수가 아니다. **상품 하나가 표 3개를 갖고 셋 다 같은 상품명을
단다.** 표본(대청 `gmgoCd=1203`, 2026-08-05)에서 등장 순서 그대로:

```
TIT    정기예탁금
TABLE  ['상품명', '계약기간', '월지급식 기본이율', '만기지급식 기본이율']   ← 수집 대상
TIT    정기예탁금
TABLE  ['예치기간', '중도해지이율', '최저이율']                          ← 수집 대상 아님
TIT    정기예탁금
TABLE  ['경과기간', '만기후이율']                                       ← 수집 대상 아님
```

**표 순서나 위치로 고르면 중도해지이율을 기본금리로 저장하게 된다.**
반드시 컨테이너(`divTmp1`)와 헤더 문자열 양쪽으로 표를 선별한다.

| 판정 | 조건 | 처리 |
|---|---|---|
| 기본이율 표 | 헤더에 `상품명`이 있고 `…기본이율`이 있다 | 수집 |
| 중도해지 표 | 헤더에 `중도해지이율` | 건너뜀 |
| 만기후 표 | 헤더에 `만기후이율` | 건너뜀 |
| 그 외 | — | 경고를 남기고 건너뜀 (조용히 버리지 않는다) |

기본이율 표의 열 배치도 하나가 아니다. 표본에서 관측된 변형:

```
상품명 / 계약기간 / 기본이율
상품명 / 계약기간 / 월지급식 기본이율 / 만기지급식 기본이율
상품명 / 계약기간 / 월지급식 기본이율 / 회전주기지급식 기본이율
```

금리 열이 둘인 상품은 **한 행이 2개의 비교 단위로 펼쳐진다**
(`payment_method`로 구분).

## 3. 기관 식별자 — 실물 확인 완료

목록 페이지는 원천값을 **숨김 span**으로 노출한다.

```html
<span hidden="true" style="display: none;" title="gmgoCd">1203</span>
<span hidden="true" style="display: none;" title="gmgoNm">대청</span>
<span hidden="true" style="display: none;" title="divCd">001</span>
```

한 행이 제공하는 필드 전체 (실측):

| title | 예시 | 용도 |
|---|---|---|
| `gmgoCd` | `1203` | **institution 키** |
| `gmgoNm` | `대청` | 금고명 |
| `name` | `대청` | 표시명 (gmgoNm과 중복) |
| `divCd` | `001` | **outlet 키 구성요소** |
| `divNm` | `본점` | 점포명 |
| `gmgoType` | `지역` | **지역금고/직장금고 구분** |
| `telephone` | `051-463-2166` | 대표번호 |
| `fax` | `051-464-0881` | 팩스 |
| `addr` | `부산 중구 대청로 101-1` | **전체 주소** |
| `r1` / `r2` | `부산` / `중구` | 시도 / 시군구 |
| `code1` / `code2` | `1203` / `001` | gmgoCd/divCd 사본 |
| `sel`, `key`, `pageNo` | (빈값) / `1` | 화면 상태값 |

### 3.1 참고 저장소보다 우위인 지점

공식 목록은 참고 저장소 JSON에 **없는 3개 필드**를 제공한다.

- `gmgoType` — 명세서 v3 §7.3.4 item 7이 요구한 "직장금고 여부를 명칭으로 확정하지 말 것"을
  공식 값으로 해결한다. 부산 중구 표본은 전부 `지역`이었다.
- `addr` — 전체 주소. 행정구역 코드 매핑과 지역 검증에 쓸 수 있다.
- `telephone` / `fax` — 기관 마스터 보강.

### 3.2 교차 검증

부산 중구 목록 파싱 결과 **9행 / 고유 `gmgoCd` 6개**.
참고 저장소 집계(중구: 금고 6, 점포 9)와 **독립적으로 일치**한다.

- `institution` 키: `gmgoCd`
- `outlet` 키: `(gmgoCd, divCd)`
- 금리는 `gmgoCd`당 1회만 수집 — 부산 기준 점포 273개 대비 금고 137개이므로 요청이 절반으로 줄고 중복 행이 생기지 않는다.

## 4. 부산 수집 목표 모집단 — **확정** (2026-08-05)

`scripts/p1c_kfcc_census.py`로 부산 16개 구·군 목록을 공식 사이트에서 직접
수집해 셌다. 보고서: `docs/source-recon/kfcc-census.json`.

```
구·군 16/16 조회 성공
고유 금고 137 (구별 합계 140)
점포 273
주소 불일치 0
```

**참고 저장소 집계(137금고 / 273점포)와 독립적으로 일치한다.** 이제 잠정이
아니라 확정 모집단이다. 명세서 v3 §13.4의 "모집단 확인 중" 표시는 해제한다.

구별 합계 140과 고유 137의 차이 3은 **같은 금고가 여러 구에 점포를 둔
경우**다. 기관 수를 셀 때 구별 합계를 더하면 3개가 중복된다.

`주소 불일치 0`은 각 행의 `addr`가 요청한 구·군을 실제로 포함하는지 되짚은
결과다. 화면 파라미터(`r2`)만 믿지 않고 주소로 검증했다.

| | | | 기장군 | 3 | 4 |

### 4.1.1 구 귀속의 한계 — 금고 3개가 두 구에 걸쳐 있다

금리는 `gmgoCd`(금고) 단위로 공시되는데 주소는 점포마다 다르다. 대부분은
한 금고가 한 구 안에 있어 문제가 없지만 **3개 금고는 두 구에 점포를 둔다.**

| `gmgoCd` | 점포가 있는 구 |
|---|---|
| 1615 | 강서구, 북구 |
| 1427 | 강서구, 사하구 |
| 1736 | 강서구, 사상구 |

현재 수집기는 금고마다 **먼저 만난 점포 행**을 대표로 삼아 주소·구를 붙인다.
따라서 이 3개 금고는 두 구 중 하나에만 나타난다. 137개 중 3개라 영향은
작지만 **"강서구 금리"를 볼 때 누락이 생길 수 있다.**

정확히 하려면 `outlets` 테이블을 점포 명부로 채우고 금리(금고 단위)와
점포(구 단위)를 조인해야 한다. `resolve_outlet`은 이미 만들어 두었으나
금리 행이 점포키를 갖지 않아(금리가 금고 단위이므로 옳다) 아직 채워지지
않는다. **미해소 항목이다.**

### 4.2 저축은행과의 대비 — 이 절단이 필요한 이유

**16개 구·군 전부에 새마을금고가 있다.** 가장 적은 기장군도 3금고 4점포다.

저축은행은 부산 전체에 점포 20개, 그것도 5개 구(부산진구·해운대구·중구·
연제구·동구)에만 있다. 나머지 11개 구·군은 저축은행 데이터가 아예 없다
(`docs/source-recon/fsb.md` §4-2).

즉 **부산 구·군 단위 금리를 실제로 채울 수 있는 원천은 새마을금고뿐이다.**
