## 2. 수집이 남은 것

### 2.1 새마을금고 요구불예탁금 (`gubuncode=12`)

화면 구조는 확인했다. 보통예탁금·자유예탁금이고 표에 **단계금액** 열이 있다.

```
상품명 / 단계금액 / 이율
MG행복지킴이통장 / 300,000 미만 / 0.1
                / 300,000 이상 / 0.2
```

금액 구간을 `amount_min`·`amount_max`로 옮기는 파싱이 따로 필요하다. 스키마에
칸은 이미 있다. 명세서 v3 §7.3.10이 완료 조건에 넣었으므로 **미룬 것이지
버린 것이 아니다.**

요청량은 금고당 1회 늘어 137회 추가된다.

### 2.2 저축은행중앙회(FSB) 수집기

정찰이 끝났다 (`docs/source-recon/fsb.md`). 엔드포인트·조회차원·필드 구조를

붙이면 finlife에 없는 것이 들어온다 — 가입방법, 우대조건 3종, 만기후이율,
상품 상세 링크. 다만 **여전히 본점 기준이라 구 단위는 안 된다.**

미해소 두 가지가 남아 있다.

### 2.3 농·축협 — 정찰부터 다시

`docs/source-recon/nh-local.md`가 "중앙 수집 불가"라고 단정했었는데
**그 판정이 틀렸다** (같은 문서 §0 정정). 농협 금융상품몰

SFDPW0160R   농·축협별 예금금리 검색
SFDPW0161R   농·축협·점포 검색 결과

정확한 HTTP 계약은 아직 모른다. v4 §5.2의 정찰(PR 3)에서 확정한다.
**파서를 추정으로 만들지 않는다.**

### 2.4 전국 수집 — 돌렸다

2026-08-06 run 31052721891에서 성공했다. 42분이라던 예상은 틀렸다 — 그 계산은
1초 간격만 세고 응답 대기를 안 셌다. 실제 요청당 3.58초여서 새마을금고만

그 실행에서 새마을금고가 `partial`로 끝났다. 9장을 건너뛰었는데 실물을 받아
보니 아홉 장 다 **취급 상품이 없는 것**이었고 구조는 멀쩡했다. 금고마다
취급 품목이 달라서 거치식만 있고 적립식이 없는 곳이 실제로 있다. 이걸
오류로 세지 않도록 고쳤다 (PR #22). 다음 전국 수집에서 `success`로 끝나는지

전국 금고 1,260 / 점포 3,135는 2026-08-05에 목록 페이지를 직접 세어 얻은

2,970점포는 참고 저장소 집계였다.

**`r1`은 행정구역이 아니다.** `r1=광주`로 조회하면 광주 101 / 전남 124 /

묶음에 가깝다. 그래서 지역 표시는 언제나 점포 주소에서 뽑는다
(`parser.split_region`, `dashboard_service.SIDO_EXPR`).

## 3. 구현이 남은 것

### 3.1 스키마만 있고 채우지 않는 테이블

| 테이블 | 무엇 | 왜 비어 있나 |
|---|---|---|
| `preference_conditions` | 우대조건을 조건별로 쪼갠 것 | 지금은 `preference_raw` 원문만 저장한다. 명세서가 나왔다 → §3.5 |
| `manual_overrides` | 사람이 고친 값 | 오버라이드 병합이 미구현 (세로 절단 5) |
| `entity_aliases` | 기관명 이형 매핑 | 통폐합·개명 처리에 쓸 자리 |

### 3.2 오버라이드 병합 (세로 절단 5)

명세서 v3 §11의 핵심인데 전부 미구현이다. 사람이 고친 값이 자동 수집값을
어떻게 이기는지, 충돌을 어떻게 표시하는지, 변경 이벤트를 어떻게 남기는지.

정적 대시보드에서 편집을 어떻게 받을지부터 정해야 한다. v3.1이 서버를
없애면서 v3의 오버라이드 모델과 어긋난 상태다.

### 3.3 교차대조 (`cross_source_difference`)

같은 저축은행을 finlife와 FSB 양쪽에서 받아 값이 다르면 검수항목을 만든다.
FSB 수집기가 선행이다. 기관코드 체계가 서로 다르다는 것까지만 확인했고
매핑은 아직 없다.

### 3.4 엑셀 내보내기

지금은 CSV와 JSON이다. 명세서 §2가 P2로 밀어뒀다. `openpyxl` 의존성을
일부러 뺀 상태다.

### 3.5 우대조건 표준화·분류 — 명세서 접수, 착수 전

[`docs/specs/20260806-preference-conditions-v1.md`](specs/20260806-preference-conditions-v1.md).
우대조건 원문을 표준 코드로 분류해 기본금리·우대금리·최고금리를 나눠
보여주는 일이다. 착수 위치는 **v4 PR 7(통합 비교 UI) 뒤**다 — 표시 화면이
그 PR에서 만들어지고, 그 위에 얹히기 때문이다.

먼저 정해야 할 것 셋(자세한 근거는 명세서 머리의 「저장소 반영 검토」):

1. **`preferential_spread`를 관측의 71.6%에서 계산할 수 없다.** 새마을금고는
   공식 화면에 최고우대금리 열이 없다(103,844건 중 `max_rate` 0건). 계산
   불가일 때 NULL로 두고 화면에 "원천 미제공"으로 적는다. `base_rate`로
   메우면 v4 §3.3과 P1-A 게이트를 동시에 어긴다.
2. **우대조건 원문이 24.8%(35,950/145,058)에만 있다.** `원천 미제공` /
   `명시적 없음(해당사항없음)` / `있음` 셋을 구별해 저장한다. 그리고
   `(고시금리 포함/미포함)` 표시를 §7의 의미보존 표현 목록에 넣는다 — 이게
   우대분이 `max_rate`에 이미 반영됐는지를 가른다.
3. **§10의 관리자 화면은 이 저장소에 런타임이 없다.** 정적 사이트라 서버도
   인증도 없다. 검수를 `review_items` + 설정 파일 커밋(PR이 곧 감사기록)으로
   할지, 관리자 웹앱을 새로 세울지는 사용자가 정한다. 지금 구조에서는
   전자가 맞다고 본다.

새 테이블은 필요 없다. `preference_conditions`(현재 7칸, 0행)를 §6의 25칸으로
넓히고, 원문은 이미 `rate_observations.raw_preference_text`에 쌓이고 있다.
그래서 §5 표준코드와 §6 칸만 먼저 넣어 두면 수집이 도는 동안 원문이 모이고
분류는 나중에 소급할 수 있다.

## 4. 운영이 남은 것

### 4.1 원본 1년 보존 — 구조적으로 미충족

명세서 v3 §16.2는 원본 최소 1년 보존을 요구한다. GitHub Artifact 상한이
**90일**이라 (2026-08-05 실측) 그것만으로는 채울 수 없다. 별도 보관소를
정해야 한다.

### 4.2 `rate-data` 브랜치 용량 — 1단계 완료

선행 수정안 v1 PR 1로 두 가지를 했다. **아직 끝나지 않았다.**

**덜어낸 것** (2026-08-06 실측, 177.67 → 74.41 MiB):

| 파일 | 크기 | 왜 뺐나 |
|---|---|---|
| `latest/export/*.json` | 50.67 MiB | 같은 내용이 `site-public/data/rates.json.gz` 0.94 MiB로 이미 있다 |
| `latest/summary.json` | 24.37 MiB → 0.15 MiB | 금리표를 함께 담고 있었다. `table` 키를 뺐다 |
| `latest/export/*.csv` | 16.57 MiB | `site-public/data/rates.csv`와 바이트가 같다 |
| `site/*.html` | 5.51 MiB × 2 | 데이터를 통째로 박던 아티팩트 시절 화면 |

셋 다 Actions 아티팩트(90일)에는 그대로 올라간다.

**이력 누적을 끊었다.** 발행이 매번 부모 없는 커밋을 새로 만들고
`--force-with-lease`로 브랜치를 통째로 교체한다. 예전에는 파일을 지우는
커밋을 올려도 과거 blob이 남아 수집마다 50 MiB가 영구히 쌓였다.

로컬 재현 실험 (3 MiB 페이로드 3회 발행):

```
옛 방식  커밋 4개  저장소 9.4 MB
새 방식  커밋 1개  저장소 3.2 MB   ← 반복해도 안 는다
```

**남은 것 — 상태 DB 50.75 MiB.** 이건 PR 1에서 못 뺐다. 워크플로우의
`Restore previous database`가 이 파일에서 DB를 복원하므로, 지우면 다음
실행이 빈 DB로 시작해 이력이 통째로 사라진다. 선행 수정안 §6.4가 금지한
바로 그 상황이다.

PR 2가 대체 경로(R2)를 만들었다. **전환은 아직 안 했다** — 계정과 버킷이
없다. `config/storage.yaml`의 `backend`가 `github_legacy`인 동안은 지금
동작 그대로다.

### 4.2.1 R2로 넘어가는 절차

세 상태를 거친다. 각 칸이 무엇을 뜻하는지는 `config/storage.yaml`에 적혀
있다.

| 단계 | backend | 복원 | 발행 | R2 실패하면 |
|---|---|---|---|---|
| 끝 | `github_legacy` | GitHub | DB 포함 | 해당 없음 |
| **지금** | `r2_migration` | GitHub | DB 포함 | 수집 계속 (빨간 X만) |
| 다음 | `r2` | R2 | **DB 없음** | 멈춘다 |

2026-08-06에 시험 단계로 들어갔다. 근거는 run 31071740056 (Storage check
(R2), 14단계 전부 success): 275,714,048 bytes DB가 20.4초에 올라가 4.4초에
되돌아왔고, 되받은 파일이 원본과 바이트 단위로 같았다. R2 압축본은
54,414,161 bytes (19.7%), `state/snapshots/20260806T043719Z-6ba3c773.sqlite3.gz`.

**아직 GitHub DB가 공식 원본이다.** `rate-data/latest/rate_monitor.sqlite3.gz`는
그대로 두고, `r2`로 넘어가 한 바퀴 정상으로 돈 뒤에야 지운다.

```bash
# 1. [끝] 시크릿과 변수를 저장소에 등록한다
#    Secrets:   R2_ACCESS_KEY_ID R2_SECRET_ACCESS_KEY
#    Variables: R2_ACCOUNT_ID R2_BUCKET R2_ENDPOINT R2_REGION

# 2. [끝] 지금 GitHub에 있는 DB를 R2로 올린다. 재다운로드 검증까지 한다
#    자격증명이 GitHub에만 있으므로 로컬이 아니라 Actions에서 돌린다:
#    Actions → Storage check (R2) → Run workflow (migrate: true)
uv run rate-monitor storage migrate --db publish/rate_monitor.sqlite3

# 3. [끝] 한 번 더 확인한다. 받아서 검사만 하고 파일을 남기지 않는다
uv run rate-monitor storage verify

# 4. [끝] config/storage.yaml의 backend를 r2_migration으로 바꿔 커밋한다
#    이 상태로 수집을 몇 바퀴 돌린다. R2는 아직 시험 저장소다

# 5. 문제가 없으면 backend를 r2로 바꾼다
#    그 순간부터 복원이 R2에서 오고, rate-data에 SQLite가 안 실린다
```

**되돌리기.** `STORAGE_BACKEND` 환경변수(저장소 Variables)가 config 파일을
이긴다. 잘못 전환했으면 커밋 없이 `github_legacy`로 되돌릴 수 있다. 단
`r2`로 한 바퀴 돈 뒤에는 rate-data에 DB가 없으므로, 되돌리기 전에
`storage restore`로 받아 두어야 한다.

**게이트가 전환을 강제한다.** `scripts/size_gate.py`는 `--backend r2`일 때
상태 DB 예외를 없앤다. 그 모드에서 파일이 남아 있으면 발행이 실패한다 —
예외가 스스로 사라지는 구조라야 "나중에 지우자"가 영원히 안 온다.

실측 (전국 262 MB DB, 로컬 왕복):

```
업로드  30.6초   262,844,416 → 52,578,941 bytes (20.0%)
복원     3.9초   원본과 바이트 단위로 동일
```

`config/regions.yaml`의 `sido_code`·`sigungu_code`가 전부 `null`이다.

### 4.6 Vercel 배포 — 한 단계가 사람 손을 탄다

산출물은 준비돼 있다. `rate-monitor build-site`가 그대로 올릴 수 있는
한 벌을 만들고, 수집 워크플로우가 이것을 `rate-data` 브랜치의
`site-public/`에 밀어 넣는다.

```
site-public/
  index.html          78 KB   요약과 조회 UI
  data/table.json    720 KB   금리표 (부산 16,913행 기준)
  data/table.json.gz
  data/rates.csv     2.1 MB   사람이 받아가는 파일
  data/rates.json    6.4 MB
  vercel.json                 캐시 헤더
  site-manifest.json
```

남은 것은 **Vercel 프로젝트를 이 저장소에 연결하는 일**이다. 저장소가
private이라 Vercel에 접근 권한을 주는 OAuth 승인이 필요하고, 그건 계정
주인만 할 수 있다. 자동화 경로로는 대신 못 한다.

Vercel 대시보드에서:

설정은 **저장소 루트의 `vercel.json`**에 있다. 대시보드에서 항목을 찾아
누르지 않는다 — `vercel.json`이 프로젝트 설정을 덮어쓰고, 그 편이 근거가
한 군데로 모인다. 대시보드 화면 구성은 바뀌지만 이 파일은 안 바뀐다.

```json
{
  "framework": null,
  "buildCommand": "",
  "installCommand": "",
  "outputDirectory": "site-public",
  "ignoreCommand": "[ \"$VERCEL_GIT_COMMIT_REF\" != \"rate-data\" ]"
}
```

이 파일은 **두 곳에 있어야 한다.** `main`의 저장소 루트(사람이 고치는
원본)와 `rate-data`의 저장소 루트(Vercel이 실제로 읽는 자리)다. 수집
워크플로우의 Publish 단계가 전자를 후자로 복사한다.

**배포 주소는 두 개다.**

| 주소 | 상태 |
|---|---|
| `bank-rate-collector-git-rate-data-dekt-oss-projects.vercel.app` | **동작한다.** rate-data의 최신 배포를 늘 가리킨다 |
| `bank-rate-collector-dekt-oss-projects.vercel.app` | 404. 프로덕션 별칭인데 프로덕션 브랜치가 아직 `main`이고, `main` 배포는 실패한다 |

짧은 주소를 쓰려면 프로덕션 브랜치를 `rate-data`로 바꿔야 한다. **이 항목은
Settings → Git에 없다** (2026-08-06 확인). Vercel이 UI를 옮겨서 Settings →
Environments 아래 Production 환경의 브랜치 설정으로 간 것으로 보인다 —
경로는 미확인이다.

바꾸지 않아도 막히는 것은 없다. 긴 주소가 같은 내용을 같은 방식으로
서빙한다. 차이는 주소 길이와, 미리보기 배포에 붙는 `x-robots-tag: noindex`
뿐이다 (검색 노출을 원할 때만 문제가 된다).

**세 가지가 실제로 걸렸다 (2026-08-06 실측).**

1. **저장소 루트를 파이썬 앱으로 오인한다.** 처음 연결하면 Vercel이
   `framework: "python"`으로 잡고 `app.py`·`main.py` 같은 진입점을 찾다
   실패한다 (`No python entrypoint found`). 이 저장소는 수집기라 그런
   파일이 없다. `framework: null` + 빈 `buildCommand`가 막는다.

2. **`main`을 배포하려 든다.** 화면 파일은 `main`에 없다. 수집 산출물이라
   `.gitignore`에 걸려 있고 `rate-data`에만 있다.

3. **PR마다 미리보기 배포가 실패한다.** `site-public/`이 없는 브랜치에서는
   빌드가 시작도 못 한다. `ignoreCommand`가 이걸 막는다 — 이 명령은
   **0으로 끝나면 건너뛰고 1로 끝나면 빌드한다.** 위 조건은 `rate-data`가
   아닐 때 0을 돌려주므로 그 브랜치만 배포된다.

**MCP `deploy_to_vercel`로는 못 한다.** 그 도구는 파일 내용을 요청 안에
직접 실어 보내는데, 전국 한 벌이 24 MB다.

### 4.7 왜 파이썬 웹앱을 만들지 않는가

정적이 더 안정적이다. 실패할 수 있는 부품이 적다 — 파일 두 개를 CDN이
그냥 준다. 서버 프로세스도 DB 연결도 타임아웃도 없다.

서버리스 함수로 만들면 요청마다 컨테이너가 뜨고 그 안에서 **262 MB짜리
SQLite**를 열어야 한다. 함수 번들 크기 제한에 걸리고, 걸리지 않더라도
콜드 스타트마다 그 비용이 붙는다. 게다가 이 데이터는 **하루에 한 번**
바뀐다 — 실시간 조회가 아닌데 요청마다 DB를 읽을 이유가 없다.

전국 132,502행 실측 (gzip 전송 기준, Vercel이 자동으로 한다):

| 회선 | 표가 그려질 때까지 |
|---|---|
| 빠른 회선 | 0.6초 |
| LTE (10 Mbps / 40 ms) | 1.3초 |
| 느린 3G (1.6 Mbps / 300 ms) | 4.0초 |
| 필터 한 번 누를 때 | 23 ms |

**웹앱이 맞아지는 시점**은 셋이다. 표가 브라우저에 다 못 올라갈 만큼
커질 때(지금 `table.json` 5.6 MB, 20 MB를 넘으면 재검토), 사용자별로
저장할 것이 생길 때(관심 상품 알림 등), 로그인이 필요할 때. 지금은
셋 다 해당하지 않는다.

## 5. 알려진 데이터 한계

- **저축은행 금리는 구 단위로 말할 수 없다.** finlife도 FSB도 본점 기준
  공시다. 화면의 구별 집계에 저축은행이 잡히지 않는 것은 의도한 결과다.
- **직장금고**는 해당 직장 임직원만 가입할 수 있다. 구 대표값에서 빼고
  따로 표시한다. 부산에 4곳 있다.
- **구 이름은 전국에서 겹친다.** 중구만 해도 서울·부산·대구·인천·대전·울산에
  있다. 집계·화면·내보내기 모두 시도와 구를 함께 쓴다.
- **`연0.0%`**의 의미가 미확정이다. 실제 0%인지 미취급 표시인지 모른다.
  값 그대로 저장한다.
- **새마을금고에는 우대금리가 없다.** 공식 화면에 열 자체가 없어 `max_rate`가
  항상 비어 있다. `base_rate`로 메우지 않는다.
